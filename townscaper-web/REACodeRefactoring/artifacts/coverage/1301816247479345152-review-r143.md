## 代码落点与差距

- `src/core/radial-patch.js#insertTemplatePatch`（文件头署本片 ID）
  - 本轮改两处，**全部在 courtyard 的环带生成路径上**，radial/block/rhombus 与接缝（原边界顶点对象原样共用）一字未动：
    1. **环带厚度均分**：旧式 `R = holeR + (minR−holeR)·innerRatio` 把 `rings` 条带挤进 45% 的环带厚度，剩下 55% 再被「拉链带 + 洞环四边格」切成两条。radius 1.9 / hole .8 / rings 5 时每条带径向厚只有 **0.05** 而弦长 0.45（长宽比 0.12）—— 细楔的**主因是过细分，不是 r142 以为的「逐点径向投影」**。现按 `s=(minR−holeR)/(rings+2)`、`R=holeR+2s` 分：rings 条环带各厚 s，剩下 2s 正好给拉链带与洞环四边格各一条。
    2. `result.patch` 增 `ringSpacing / minRingRadius / holeRingRadius` 三个读数（页面可复算 `R == holeR + 2s`）。
  - **试过并回退**：把 courtyard 的目标环也改成 radial 那条**严格等角环**（`phase+i·2π/N`，r142 的建议）。实测在**不规则四边形边界**上，第一圈带的四边格会翻折（`grid.radius=12, seed=5, x=4.5, radius 2.7/3.1` 直接抛 `unsafe patch geometry`），且长宽比只从 0.595 抬到 0.620 —— 收益 4%、代价是原实现能过的配置开始拒绝，故不采纳（另试「目标角夹紧到半扇区 + 极坐标插值」，仍有 2 例翻折）。这也纠正了 r142 的因果判断。
- `gridpatch.html`：原片口径深链改为 `?template=courtyard&rings=5&radius=2.6&hole=.6`（radius 1.9 + hole .8 的环带只有 1.2 格厚，装不下 5 条方格带，是自相矛盾的口径）；`#report` 增 `ringSpacing / ringInner / ringMin / ringHole / outerCells / outerEdgeRatioP50 / outerSlivers`（外环带与中心过渡带分开报，不混口径）。
