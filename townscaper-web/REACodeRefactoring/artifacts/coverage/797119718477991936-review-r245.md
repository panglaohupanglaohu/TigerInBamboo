## 判定

有机制：地表导航 + 分层节点（同柱多层、洞顶不算地面）+ Battle 接线（r237/r238 已验：封洞 `distance 0`、
不封洞必须穿洞 `tunnelSamples 185/194`）。门价按「跨几个洞口」收（r238）。

本轮补的是门价没有的那一半：**谁此刻在洞口**。r238 的收尾写着「拥堵导致的动态排队仍不在导航层」——
这是本片与 `906425294533394432` 共用的最后一条缺口。

设计判据（不发明片里没有的东西）：
1. 拱洞宽 = 多人并行（片内 5–6 球径），所以容量**按实际净宽算** `floor(净宽 / (2·体径+缝))`，
   宽口仍多人同时过 —— 与片内观感一致；
2. 窄口（净宽 ≈ 2 体径）才退化成单列，这正是「洞口」这个词的物理含义（最窄断面是闸口）；
3. 洞身内部不设闸（r238：门价只在跨洞口收，洞身平价）。

## 代码落点与差距

- 新增 `src/world/door-occupancy.js`：`DoorOccupancy`（占用表 + FIFO 队列 + ttl 兜底 + `capacity(width,radius)`）。
  一人一次只占一个洞口；换洞口自动释放；`sweep()` 清掉死者与消失的排队者。
- `src/world/battle-navigation.js`：新增 `mouth(a,b)`（同层、一侧 `covered` 的格边 → `{key,width,x,z}`，key 双向同值）
  与 `mouthStats()`（洞口数 / 窄口数 / 最小净宽）。
- `src/badnorth/battle.js`：走路分支过洞口前 `claim`；被拒 → 这一步不迈（停在洞前，`doorStats.waits++`）；
  「占着洞口却挪不动 > 0.3s」→ 主动放行（对面堵死时两边互等的唯一出路，`doorStats.stalls`）；
  离开洞口/掉头/到位立刻 `release`；每帧 `sweep` 清死者。`battle.doorReport()` 是只读账；`?doors=0` 关档。
- 差距：**片子不显示排队**，所以「窄口单列」只能靠净宽推，不能拿片内时序标定；本仓不据此改 `doorCost`（仍 1.35）。
