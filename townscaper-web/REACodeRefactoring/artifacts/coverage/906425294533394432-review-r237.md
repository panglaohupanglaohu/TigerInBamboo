### ① 为什么红：夹具把「桥面」写成了岩石台地

旧夹具第 7 行：

```js
for (const c of w.cells) { w.fill(c,1,{rock:true}); if (Math.abs(c.cx)<1.4) w.setSolid(c,3,true,{rock:true}) }
```

`setSolid(...,{rock:true})` 把第 3 层同时写成 **rock**。`world.ground()` 取的是**最高岩石层**，
于是中间那一列变成 `top=3 / ground=3` → `buildNav` 的 `walk[]` 判据 `t===g` 成立 → **桥顶被当成「裸露台地」**，
`stairs` 里就多出两道 `rise:2` 的楼梯（实测 `(-1.67,-0.12)→(-1.38,-0.53)` 与 `(1.68,-0.25)→(1.29,-0.06)`）。
走屋顶与穿洞同价甚至更短，所以 `maxY ≤ 0.51` 的断言必然失败。

### ② 量化「走屋顶」到底怎么发生的（旧夹具实测，480 帧轨迹）

```
k=50  x=-2.10 z=-0.30 y=0.500 floor=1    ← 还在平地上，plan 走洞底
k=60  x=-1.96 z=-0.35 y=0.500 floor=1    ← 这一帧 plan 换成上桥：next.floor=3
k=90  x=-1.64 z=-0.66 y=1.270 floor=1
k=100 x=-1.52 z=-0.74 y=1.457 floor=3    ← 顺 2 级楼梯登上桥面
k=130 x=-1.08 z=-0.82 y=1.500 floor=3    ← 桥顶行进
k=350 x= 1.84 z=-0.06 y=1.060 floor=1    ← 下桥
k=450 x= 2.99 z=-0.01 y=0.500 floor=1    ← 到达
```

即 `pathMaxY 1.55 / maxY 1.50 / tunnelSamples 0`，而 `remaining 0.14` 说明「到达」这件事是对的、
**路线换成了屋顶**。这是 `buildNav` 的既有设计（地形量化到偶数层，一道崖 = 2 层，`MAX_STEP=2` 允许一级台阶爬一道崖），
不是 `steerTarget` / `portalAim` 的接线 bug。

### ③ 试过并回滚的错误假设（不写进代码）

先按 `next` 里「1→3 楼梯边比隧道便宜」的字面理解，怀疑是 `stairAt` 的**踏步矩形把路过的队伍吸上桥**
（`footHeight` 只看脚下 XZ 在不在踏步里）。落了一版 `unit.navToFloor` 闸门（Battle 每帧把 plan 落脚层写给
`footHeight`，同层行进不许踩踏面），**读数逐位不变**（三次运行 `remaining 0.14021524394482063` 完全一致）→
假设被否：抬脚不是「吸」，是 **plan 自己换的**（k=60 那帧 `navToFloor` 从 1 变 3，先换 plan 后抬脚）。
源码已完整回滚（`src/badnorth/battle.js` / `src/world/battle-navigation.js` 现与本轮开工前一致，`grep "第 237 轮" src/` 无命中）。

### ④ 落地：把桥面改回「建筑」

```js
for (const c of w.cells) { w.fill(c,1,{rock:true}); if (Math.abs(c.cx)<1.4) w.setSolid(c,3,true) }   // 去掉 {rock:true}
```

`top=3 / ground=1` → `topIsBuilt` 成立、`walk=0` → 桥顶不可走、`stairs` 里不再有 `rise:2` 的边，
第 1 层的洞道成为唯一通路。夹具语义恢复成片里的形制：**厚岩拱洞，顶上有实心，洞里能走人，但没有坡能上顶。**

### ⑤ 顺带修掉的两处等待签名（真 bug，不是调数字）

`p.waitForFunction(fn, {timeout:60000})` 在 Playwright 里第二个参数是 **arg** 不是 options，
所以三处「60 秒」实际一直是默认 **30 秒**（本机 swiftshader 在负载高时首帧要 40–90s，于是随机红/白等）。
改成 `p.waitForFunction(fn, null, {timeout:120000})` 后不再出现假的 TimeoutError。
