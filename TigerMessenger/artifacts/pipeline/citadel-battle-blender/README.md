# 高山圣城之战 · Blender 目标图复刻 v1

目标图：`assets/concepts/citadel/citadel-battle-target-v1.png`（用户 2026-09-10 认可）。
本目录是**独立候选**：没有改主线 Web/Godot 生产文件、存档或既有 citadel 资产。

## 实际执行方式

本会话没有 macOS shell，只有 Blender 图形界面可达。因此在前台 Blender 的 Python
控制台执行了一次 `tools/pipeline/mac_job_runner.py`，它注册一个轮询器，把
`jobs/*.job.json` 交给**独立的后台 Blender 进程**
（`--background --factory-startup --python`）运行。前台场景全程未被修改、未被保存。
每个任务留有 `.log` 与 `.done`（含 returncode 与耗时），可逐条复查。

Blender 5.2.1 LTS，EEVEE。真实执行，不是"计划"。

## 与目标图仍有的差距（未达标，不当作完成）

1. 城门内芯仍偏白，不是目标图那种橙红渐层；`gate_glow` 自发光与曝光的平衡还需再调。
2. 水面金红长倒影仍是散斑，不是目标图的连续长条。EEVEE 屏幕空间反射对屏外光源无能为力，
   需要改用反射探针或给水面单独做条状自发光倒影贴片。
3. 木马造型粗糙，比例与目标图的编条木马差距明显。
4. Blender 5.2 的合成器改成节点组后，Glare 泛光接上会输出空帧，已关闭合成；
   目标图的柔光晕当前只靠自发光 + AgX，弱于参考。
5. 旧城密度、粉紫色调与目标图左上角的发光簇仍有距离；远山只有 4 层脊线，
   没有目标图的雾层过渡。
6. 士兵是静态玩具体块，没有骨骼、动画、碰撞，**不是**游戏里实际使用的士兵资产；
   本轮没有把任何资产接入 Web 或 Godot。
7. 渲染时 EEVEE 报 "shadow atlas 3076 / 2048"，阴影图集超限，需要减少投影灯数量。

## v2 修订：城门色阶与水面倒影（本轮专攻两项）

### 城门
上一版把发光拱直接贴在实心墙面上，**墙上根本没有洞**，所以做成隧道后灯光被埋进实体里、
门洞发灰。本轮把主体块整体后移 4 m，另建一道 4 m 厚的**分件前墙**（左右墙墩 + 过梁 +
拱券环），门洞是真的通的。洞内放 5 圈 `arch_band_data` 生成的拱形环带，沿进深依次后退
并逐级升温（0.55→1.0→1.7→2.6→4.6 强度，色相由 (1,0.18,0.04) 推到 (1,0.60,0.22)），
最深处是一块占洞口 80% 的金色亮板，另有 6 段递窄的发光地面和两侧门墩投出的阴影线。
灯光从"一盏猛灯洗墙"改成深处热源 + 门口溢光 + 立面暖光三盏。

### 水面倒影
EEVEE 的屏幕空间反射看不到点光源，也看不到画面外的东西，所以目标图那种金红长条
**不可能靠 SSR 得到**。本轮改成把倒影当几何体做：`water_reflections()` 为每个暖源沿
"光源 → 相机"方向铺一条发光卡片带，卡片在靠近观者一端逐渐变宽、变暗，带随机抖动和
约 22% 的断口，模拟真实的碎光路径。共 2,238 张卡片，分 hot/mid/dim/far/cool 五级材质。
两个关键修正：相机几乎就站在岸线上，纯视线方向的倒影会顺着码头跑，因此方向额外向
外海偏置 0.62；并加了岸线遮罩，卡片绝不落到码头上。

同时修掉两个本轮才暴露的问题：码头发光条尺寸过大、亮度过高，在港口视角是一排白色广告牌，
已缩成小灯箱；多盏点光源半径 1.2–12 m，在水面糊出白色大圆斑，半径收到 0.18–1.0。

### 这两项仍未完全达标
- 倒影卡片在 1920 全分辨率下仍看得出是矩形碎块，不够连续柔和；要更像目标图得换成
  带渐变 alpha 的条带或真正的平面反射。
- 远岸与冷色倒影偏弱，几乎看不出。
- 城门口对立面的暖溢光比目标图弱，白墙仍偏冷。

### 第 3 项 水面（部分完成，`src/world/citadel/westCity.js`）

## v5：相机遮挡回拉（第 4 项，已实现但**未证明**修好用户遇到的那一例）

### 查到的事实
`src/core/camera.js` 的第三人称装配把相机固定摆在身后 `camDist` 处，**完全没有遮挡检测**——
没有射线、没有回拉。所以只要有实体挡在相机与信使之间，画面就会被糊住，这是结构性缺失。

真正挡住玩家行走的不是资产碰撞球（全场只有 63 个球、其中半径≥1.2 的仅 7 个，都是道具），
而是 `src/world/citadel/playerWalls.js` 里按名字取的 6 个**具名墙体网格**：
`tower-interior-solid` / `main-gate-wall` / `main-gate-carved-surround` /
`court-solid-stone` / `processional-solid-stone` / `processional-solid-coping`。

### 已实现
- `playerWalls.js` 导出 `CITADEL_WALL_MESH_NAMES`，并新增 `createCitadelCameraOccluders(city)`，
  返回"离给定点一定范围内的墙体网格"短列表。行走碰撞与相机回拉从此共用同一份名单，不会各自漂移。
- `camera.js` 增加两级遮挡检测：先用碰撞球做解析线段求交（极便宜），再对上述墙体网格做射线。
  沿"看点→期望机位"收短，保持取景方向不变；被遮挡时收得快（t×2.4）、恢复时按原速放，
  避免在门洞口抽搐。玩家已在球体内部的球跳过，否则"人在屋里"会把相机顶到墙上。
  下限 2.0 米、命中点前留 0.55 米余量。新增 `setOcclusionEnabled` / `getOcclusionDist` /
  `setOccluderMeshes` 供验收与关闭。
- `main.js` 在圣城加载处注册遮挡网格提供者。

### 验收结果：机制有效，但没复现出用户那一例
- 把信使摆在大体量墙旁、相机被推向墙体一侧时：开启回拉 `camToPlayer` 14.94→**7.32**，
  关闭则保持 14.94。机制确实在工作。
- 但沿**真实攻城路线**（`highlandAssaultAnchors.stairRoute` 86 点）与**塔内各层路线**
  （`interiorFloorRoutes`）逐点采样，各 29 个采样点，**开关两种情况下"石头挡住信使"都是 0 次**。
  也就是说这两条已授权路线上，那 6 个具名墙体从来没有真的挡住过相机。

结论：回拉是净改进且无回归（无遮挡时 `free === rayLen`，行为与改前完全一致），
但**不能据此宣称第 4 项已修好**。很可能用户进的是新城那些蓝顶民居/主堡内部，
而那些网格根本不在这 6 个名字里。需要用户指明是哪栋建筑、从哪个门进去，
才能把正确的网格接进遮挡名单。

## 第 5 项 旧城朝向：未动，等用户确认转向
