这是只读接口与范围方案；轨道、山体、瀑布、车辆源码均未改。用户最新方向替代旧前景湾环，剩余侵轨分类已停止。原捕获数据与审计保留。捕获方式及 CUA 限制见 `REVIEW.md`，本次增量只有 CPU JSON 分析和源码阅读。

## 最新用户合同：中央联络桥上步行、下铁路（覆盖下文旧内岸联络主线）

中央现有步行桥的走向与桥面保持；新旧城联络采用同一中央跨湾桥的上下双层交通。下层红蓝双轨连续接两城贴崖洞廊，不再把绕后湾内岸长绕行作为两城主联络。旧内岸侦察点保留作岸线证据，不再代表拟定轨道走向；原前景外圈拆换范围与全球线接口约束仍适用。

下层标高必须以旧城瀑布洞廊轨面、中央桥原上层步面和新城贴崖轨面的实际世界坐标联合求解。先固定上层桥，再沿其实际路径采样径向/轨道up净空，求平顺可行的下层纵断面；不能以城堡localY固定下移或任意斜线连接。对每条红蓝线验证坡度、坡变/竖曲率及整列动态包络；若没有连续满足条件的解，报告冲突并调整两侧洞廊接点，不能暗中抬高或拉歪原步桥。

现上层约4.4m宽，实际双轨联合净宽试算约8.74m，不能直接把铁路塞进旧桥墩之间。原桥墩可能堵住纵向铁路空间：需要独立双侧承重/门架或明确贯通桥墩洞口，并保留通船孔。上层可比铁路窄，但顶板、承重与海侧边缘应有完整横断面。瀑布水帘洞位于旧城接入段：水流由真实伸出水槽跨过顶板后在海侧落下，双轨位于岩壁和水帘之间。

未求解下层轨心或标高，未改桥、轨、瀑布及车辆。下文“旧城内湾岸线→后湾凹口→新城西侧壁”的旧主线建议已被此合同取代，仅两城各自的贴崖接驳段继续使用岸线约束。

## 拟改接口与精确保留方式

现工厂 `buildChristchurchTramSystem` 在全局1440等弧长重采样、多轮平滑、投影后生成 center，再生成红/蓝平行线，之后统一建立轨道、桥面、站台、车辆。仅修改 `COASTAL_TRAM_CONTROLS` 会改变全局弧长采样点和多个平滑阶段，无法证明别处轨形不变。

建议增加显式可回退 `opts.citadelRailPlan`，在**旧最终 center/red/blue 已生成，但 addTrackLane/addViaductDeck/车辆尚未构造之前**应用局部曲线组合器。拟接口：

`createCitadelRailSplice({sourceCurves, castleMatrix, anchorWorld, innerCorridor, stationManifest}) -> {curves:{center,red,blue}, changedSegments, remapDistance, stationManifest, report}`

- 外段直接委托原曲线原参数区间，保留其世界轨形，不重新拟合完整闭合曲线。新段与两端 world位置/切线相合，接头至少C1；全局新曲线按各段实际长度组合。
- 中心、红、蓝三线一并发布。红蓝新段按现±2.05m中心偏移生成，但接头分别与对应旧线准确衔接；不可将红蓝相同u当同一横断面。
- 轨道、枕木、洞廊、支撑、车辆与站台都引用同一个新方案。不要在旧轨之上另放一条装饰铁路，也不能只隐藏旧轨、让车继续旧路线。
- 保存原路线对象、方案版本及明确改动区间。默认撤回参数恢复原工厂路径。未改动世界点应对照旧曲线逐段同位置验证，不能比较新旧相同全局u。
- 最小安全接入是页面启动构造时应用，玩家仍从书店出生。此时车辆、loadingStops、interlocking、音频区段全按新曲线初始化，避免运行中半更新。

若后续要求不停机热替换，另需原子事务：新几何脱离场景准备；整列车、玩家及搭乘相机不在受改区间，且列尾11节×7m≈77m加缓冲全部离开；再同时换曲线、trackLen、站台与联锁。旧进度按旧弧长距离映射到新距离，不能保留原归一化progress。区间内车辆应推迟切换，不能传送到新线。当前没有该热替换接口，不能声称已具备。

## 车辆和站台必须同步的真实接口

`tramSystem.js` 的 service.curve、trackLen、progress、loadingStops、canyonMask、freightJunctions/interlocking、wagons与couplers均依赖路线。车头/车厢位置按各自曲线弧长和7m车距求得，保留稳定 red/blue vehicle 实例与方向1/-1。重算长度与进度映射还须维护停站名称、lastStop/dwell、货运控制器订阅；书店装卸站坐标与动作不改。

当前 `coastalTramStructures.js` 把站台布局、步行连接和 `citadelTramAlight` 放在两套查询逻辑中；alight 使用castle XZ距离14m，新方案不可照搬，否则上下重叠支路或上层步道会误触发。建议统一 `stationManifest`：稳定id(new-city/old-town)、所在routeSegmentId、lane、world站台/轨道锚点、3D允许搭乘范围、实际foot出口、上下层连接。站台几何与alight读取同一manifest；运行时沿正确支路3D距离判定，并验证完整身体下车点。上下车应保留真实F键流程，出口落在已通过承托的步廊或阶梯，不直接放回旧坐标或用虚拟地面接人。

## 双层交通和瀑布水帘洞合同

用户指定铁路在岩壁与向海探出的水帘之间。瀑布从现有上游水渠经有真实底板的伸出水槽/溢流唇移到海侧，再落入海中；铁路从后方有洞廊顶板保护的干燥空间穿过。不能以轨道与水帘相交作为成功。

每个横断面使用实际轨道 up/right/tangent 定义：岩壁 → 铁路及侧向净空 → 海侧洞廊开口/水帘 → 海面。上层步行廊与顶板相连，留独立栏杆及两端上下行接头；顶板必须有山侧承托或真实拱/墩，不能只放悬浮挡雨薄片。

现有联合保守车体半宽1.72m、最高点轨心上2.642m。双线最外缘距离center约2.05+1.72=3.77m；若暂以每侧0.6m试验余量，净宽至少8.74m。上方按实际车辆最高点+动态/装载余量+顶板厚度决定步面高度；例如空载当前包络+0.5m净空+0.6m结构厚度约3.742m，仅是候选计算，未来机器人/货物/集电装置未量完，不能直接定施工标高。

水槽底板、溢流唇和动态水帘的三角/体积应与全部列车包络分离；落水冲击、泡沫及海侧排水离开轨面，水帘还需保留波动余量。瀑布段通过条件应分别列出：列车干燥净空、上层步面承托、桥墩/岩壁实体支撑、海侧落点、原供水连续性、相邻船体及航路有限检查。透过透明水材质看见车，并不证明轨道没有穿水。
