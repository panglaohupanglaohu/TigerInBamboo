打开 http://localhost:8931/TigerMessenger/ 应直接进入优化后的原游戏，不显示 Godot 跳转按钮或测试大厅。已撤掉跳转按钮，发布辅助脚本不再修改原入口。Godot 导出与大厅只作为开发诊断，不能代替原游戏交付。

# TigerMessenger 改进合入与测试发布流程

版本：2026-09-10。适用负责人：Astra、后续接手模型及人工开发者。本文可直接收入知识库。

## 目标与唯一验收入口

用户从 **http://localhost:8931/TigerMessenger/** 进入，点击“Godot 新版测试 · 圣城 / 苔庭”，在当前浏览器标签页运行同一个 Godot 工程。原网页版保留对照。Godot 桌面用于编排和诊断；Web 发布用于用户实际测试。二者来自同一份 `godot/` 工程，不能分别维护两套士兵、战船或战斗规则。

一次合入以“可测试的区域或功能”为单位。例如“苔庭伏击：同一拨士兵登岸→松下隐藏→信号→发现→反击”，而非“导出20个模型”。原世界、美术方向、角色身份、原剧情规则始终作为依据。实验场景只能用于验证，不能替代原作世界。

## 必须区分的状态

**已索引 → 已读源代码 → 已建立优化候选 → 已导入 Godot → 已在实际场景接入 → 已通过针对性测试 → 已发布 8931 → 用户验收通过。**

目标图、Blender 渲染和资产检视只证明美术或资源阶段；不能证明战斗已经使用。Godot 桌面检查通过不等于 Web 通过。自动测试通过不等于人工美术和音效验收通过。每个状态附文件、版本和证据，不用资产数量代替完成率。

## 合入步骤

| 步骤 | 具体做什么、怎么做 | 必须交付的东西 | 进入下一步的条件 |
|---|---|---|---|
| 1. 确定本批范围 | 选一个实际区域或功能；列用户目标、原作规则、涉及资产与现存缺陷。核对 PLAN、TODOS、PROJECT_HANDOFF 最新记录，历史段落不当最新状态。 | 批次记录、资产清单、明确的人工测试路线 | 清楚“用户进去后应看到什么、能操作什么”；未实现部分明确列出 |
| 2. 锁定基线 | 保存当前可运行版本的 Git 提交或变更清单；记录源模型、优化模型、脚本路径和 SHA256。工作区已有改动不能被覆盖；只提交本批文件。 | 基线标识、原场景截图、可恢复的模型/适配器版本 | 能恢复上一可测状态；源文件和候选明确分开 |
| 3. 优化与技术并行 | 美术按认可参考图在 Blender 候选中迭代；技术核对骨骼、握点、单位、正面方向、碰撞和剧情接口；两线使用相同资产 ID。互不写同一资产文件。 | `.blend`、导出 `.glb`、装配元数据、参考图、前后对照 | 模型结构和方向满足引擎接口；不是只通过摆拍 |
| 4. 导入共享资产库 | 将可用候选放入 Godot 正式资源目录，统一资源引用。保留节点 ID、动态部件及材料；旧候选保留但不作为运行默认。 | Godot 可加载资源、版本映射和导入记录 | 无缺贴图、失效骨骼、乱码、破坏节点引用等错误 |
| 5. 接入实际区域 | 在原场景中替换实际工厂/适配器引用，保留原位置与身份。士兵船上与岸上同一拨；武器所有权、动作与碰撞跟随。不能只改 review 页面。 | 场景、适配器与运行引用；实际游戏内截图 | 用户进入该区域就能看到新版；禁用候选时能恢复基线 |
| 6. 接通行为和故事 | 使用原触发条件，接正常进入、任务选择、实际距离/命中、状态推进、结束和重置；BGM 由当前区域及战斗状态控制。 | 正常交互路线、状态转换说明、保存/重置策略 | 正常交互可到达新行为；不靠调试刷兵或计时冒充胜利 |
| 7. 做针对性检查 | 检查本次改动的真实风险：握持、通行、阻挡、状态顺序、旧引用、声音切换；先资源检查，再单人/局部，最后一次区域集成。重型测试串行。 | 自动测试结果、实际运行截图/动作记录、已知限制 | 必要检查通过；失败记录不删除，不以静态截图替代动画测试 |
| 8. 加入统一测试入口 | 把实际场景接入测试大厅；按钮写明可测内容和未完成内容。同一运行实例切换，先释放旧场景及音频，再加载下一场景。 | 可点击场景入口、操作说明、返回/重置 | 进入→操作→返回→再次进入可用；不残留上一场景对象/BGM |
| 9. 导出 Web 候选 | 使用匹配 Godot 版本的官方 Web 模板，同一项目导出。正式流程先导出到独立候选目录，检查完整性后发布；不要边导出边覆盖用户正在运行的版本。 | HTML、JS、WASM、PCK、版本说明 | 导出成功，依赖和中文字体齐全，磁盘空间够；不能只检查 HTML 存在 |
| 10. 在 8931 同源验收 | 使用实际浏览器加载候选，检查资源状态、中文、画面、鼠标/键盘、切换、重置、BGM和至少一条核心交互。Godot Web 与桌面分别记录。 | 浏览器截图、控制台结果、操作测试记录 | 没有阻塞性加载/脚本错误；主要功能可用，性能限制如实记录 |
| 11. 发布与人工验收 | 将入口指向通过测试的候选版本，保留上版入口。用户在原地址刷新，进入新版测试。提供“本批改变、怎么测、已知问题”。 | 发布版本、固定入口、用户验收清单 | 用户反馈分别归为缺陷、偏好、后续范围；只有用户认可后标为验收通过 |
| 12. 收口和接续 | 把最终引用、测试结果、发布位置、回退方法、剩余问题写入交接文档。下一负责人从这条记录继续。 | 批次报告、更新后的 PLAN/TODOS/HANDOFF | 不依赖聊天记忆；下一条工作具体可执行 |

## 验收示例与不可破坏的规则

- **圣城**：选择某兵种通行演练，确认模型、装备和移动；插入阻挡必须停住；重置不留旧角色。当前246段通行通过，不等于全军攻城完成。原五台地/云梯已停用，不能重新启用；62秒不是自动胜利；木马夜潜8人和战后巡逻6人不能混为一谈。
- **苔庭**：士兵到达并隐藏后才能发信号；舰队发现鲲后再伏击。只有机队实际受到攻击才允许重甲空降。检查鲲反击、结束、重置；登岸/蹲姿不完善必须标注。
- **声音**：当前区域拥有BGM控制权；离开苔庭或返回大厅应停止其BGM。武器音效有并发上限、距离衰减、优先级；不能几十名士兵同时叠加同音量。音效仍需要人工试听，不以日志代替。
- **美术**：认可参考图→Blender→Godot→Web同机位对照；头盔方向、裙甲、手掌握点、船艏朝向、树干面色等均在实际使用姿态下核对。

## 失败与回退

资源或行为检查失败：留在候选，不替换默认引用。Web 专属失败：保留桌面成果，但标记“未发布”，不能宣称用户已能在8931看到。发布后发现阻塞：入口回指上一通过版，保留失败候选和错误记录；不删除原模型、不重置用户原 Web 存档。涉及存档格式的改动必须先备份及明确迁移策略。

后续发布需实现“版本目录 + 一处入口切换 + 上版保留”。本轮首次导出写入 `godot-web/`，该版本化发布自动化尚未实现，不能把本文规划当成已有系统。

## 资源使用纪律

最多一个编辑器与一个测试实例；不累计打开 Godot；不并发加载多份完整球体。每次重型测试结束核对进程退出。保留编辑器未保存内容。空间不足先查本次临时输出；历史临时文件仅在确认无人使用且与原文件校验一致后清理，不能泛删用户下载、模型或版本。

并发适合资产分析、美术候选和独立逻辑开发；合入、场景运行、导出发布由一个负责人串行收口。当前大包首次加载偏重；后续按区域拆包、LOD、音频流式加载另开性能批次，不在合入时偷偷改变原布局。
