# Oskar 两款已发布游戏：技术证据与可复现设计

研究日期：2026-10-04。范围：Bad North、Townscaper 的公开一手材料及原始算法代码；未取得两款游戏私有源码。本文件补充 `OSKAR_ADVISOR_COMPARISON.md`，不取代主代理的 X 媒体观看记录或大会逐段研究。这里的“已读”指文字或代码阅读，不计作观看 GIF 或完整演讲。证据索引见 `artifacts/research/oskar-deep-20261004/games.json`。

## 1. 哪些事实可以确定

**WFC 与 MC 各司其职。** WFC 原作者仓库明确列出 Bad North 的导航选择启发式，以及 Townscaper 对 WFC、Marching Cubes 和非规则网格的组合。原始 `Model.cs` 可见候选域、观察、支持计数传播与矛盾返回；这份开源算法代码不是 Oskar 的游戏代码。不能把使用 WFC 简化为“随机拼块”，也不能把 MC 当成生成宏观山势的保证。[G01 原仓库](https://github.com/mxgmn/WaveFunctionCollapse)、[G02 原代码](https://github.com/mxgmn/WaveFunctionCollapse/blob/master/Model.cs)

**Bad North 的地形先服务通行。** 2022 年作者采访描述手工地形模块、接口扫描及玩法约束；作者明确承认模块内部通行模型的局限。Townscaper 则让玩家控制大形，细部自动变化，细长支撑偶有匹配失败。这些是可借鉴的设计及应避免的局限，不是本项目接受悬空轨道的理由。[G03 作者采访](https://www.gamedeveloper.com/game-platforms/how-townscaper-works-a-story-four-games-in-the-making)

**Townscaper 的不规则布局有作者亲述流程。** 作者 2020-06-01 的 Imgur 开发文介绍：六边形中的三角网格，随机合并相邻三角形，细分为四边形，再松弛；标准模块随后适配倾斜单元。本轮通过搜索索引读到这些正文段落，直接页面只返回 JavaScript 提示，因此不记作完整文章或动态图观看。[G04 作者开发文](https://imgur.com/gallery/instant-town-building-i364LBr)

**Townscaper 已发布更新中包含手工特殊网格与可调阳光。** 作者 2020-10-07 公告列出环形、对称、方形特殊区以及可调太阳角度，也记录网格变更可能破坏存档。说明“有机生成”仍可保留作者设计区域；配色不能脱离照明；网格版本是存档兼容的一部分。[G05 作者更新公告](https://store.steampowered.com/news/posts/?appids=1291340&enddate=1606383944&feed=steam_community_announcements)

## 2. 新的一手证据：Bad North 运行架构与角色周边系统

联合开发者 Richard Meredith 在 2017-07-23 的博客明确描述 Bad North 的 **flow field**：角色把邻近信息注入导航网格，数据传播并衰减，供系统采样。他把更新移到独立线程，并分离输入、工作数据和结果。文中承认有流水延迟，且现在页面提示 Unity 5.5 实现已经过时。这里的 flow field 是动态邻近信息场；不能直接说它等于目标寻路梯度，更不能说它是 WFC 生成骨骼动画。[G06 开发者技术博客](https://www.richardmeredith.net/blog/simple-multithreading-for-unity/)

同一开发者 2017-11-09 描述生成队列、后台任务、主线程构建、评分及失败重试，并解释当时从离线筛选种子走向提前后台生成。这个时间点早于正式发行，应表述为开发期架构证据，而非证明后续每个版本完全相同。其公开 `ThreadWorker` 示例提供暂停/取消机制，但作者也提醒旧实现过时，不能照搬旧线程 API。[G07 开发者技术博客](https://www.richardmeredith.net/blog/pausing-resuming-aborting-threads/)、[G08 关联示例代码](https://gist.github.com/rtm223/f1eb1360beba7bef11fae4ca8624f32e)

这补上了此前缺失的一层：程序化世界不是只运行一次求解器，还要安排生成、构建、取消、验证和运行期数据。**尚未得到 Bad North/Townscaper 使用 WFC 生成角色关节运动的原始证据。** 可以研究时间方向约束编排，但须作为我们的试验，不能将角色移动画面升级成算法证明。

## 3. 不要混在一起的概念

| 概念 | 输入与输出 | 本项目采用方式 | 证据边界 |
|---|---|---|---|
| WFC | 候选模块及兼容表 → 局部一致的选择 | 为地形/建筑选择合法变体 | G01/G02；不自动保证宏观主次、全局道路或物理承重 |
| MC / 局部占据模式 | 角点状态或标量场 → 表面组合 | 用于需要的体积表面；建筑可选手工局部模块 | G01/G03；不把标准光滑等值面直接当 Townscaper 建筑实现 |
| 主网格/对偶网格 | 拓扑关系 → 不同语义承载位置 | 玩法路径与地形过渡解耦 | 作者 2021 通用说明；不声称两游戏所有系统都如此 |
| 网格松弛 | 顶点位置及约束 → 较均衡单元 | 锁定边界与硬崖，再调局部单元形状 | G04 可证其使用松弛，不能由此推定特定 MCF 公式 |
| 模块变形 | 标准模块坐标及目标单元 → 实际几何 | 使用可校验的映射并重算法线 | G04 可证需要适配单元，具体公式下文是项目选择 |
| 连通约束 | 门、坡道、路径入口 → 可达关系 | 单独检查内部连接与全局可达 | Bad North 启发式说明不等于普适全局证明 |
| 动作/转向/瞄准 | 目标、速度、接触及武器状态 → 姿态 | 保留运行期运动与动作系统 | G06 只证实邻近信息场，不证实 WFC 动作引擎 |

作者 [2021 双网格帖](https://x.com/OskSta/status/1448248658865049605) 的[已读文字镜像](https://threadreaderapp.com/scrolly/1448248658865049605)区分玩法主网格和表现用对偶网格（G09）。2022 草片和 2023 混合地形实验，以及 2024 树云实验，应留在后期研究中，不能倒填为 Bad North 2018 发行版功能。

## 4. 可复现引擎方案：项目设计，不是私有实现复原

### 4.1 冻结可重复输入

每次生成保存 `seed、topologyVersion、moduleCatalogHash、constraintHash、materialProfile、surfaceRevision`。输入包括作者确定的山脊/岩台或城堡大形，铁路扫掠体、港口步行口、城基固定点。相同输入版本应输出相同模块选择和拓扑；不同视角或运行帧数不能改变结果。

先在有限局部区域做复现，避免先追求无限世界。铁路附近保留确定的边界，不随机更换整座城的拓扑。输入损坏、失败和取消分别返回，不用永远转圈的重试掩盖模块库问题。

### 4.2 模块库与拓扑适配分离

一个模块至少包含：参考网格、边界曲线、材质语义、上下承托、净空体、可种植多边形、通行入口及**模块内部入口连通表**。门洞左右两个接口存在，不代表它们在模块内部相连；高低台之间也不能只靠相同标签认定可通行。

建立真实的海蚀脚、窄凹槽、宽台面、硬崖、坡肩、鞍部、破碎顶模块。城堡建立台基、拱门、楼体、翼楼、墙角、楼梯与屋顶衔接模块。先人工组合通过近远景轮廓验收，再授权求解器选择它们。几何里没有足够宽的台面，任何熵权重都不会补出来。

### 4.3 约束求解与全局验证

以接口方向、边界高程、承托与材料接缝编译兼容表；旋转、镜像必须同步更新语义。固定的道路/港口为空间禁入或钉选条件。求解器删除无支持候选，选择未确定单元，传播；冲突使用有限回溯，预算耗尽返回冲突区域。

求解途中可维护“候选仍有可能连接”的乐观路径图：目标间已经无路，则提前拒绝；存在路只是必要条件，不是最终成功证明。完成后使用实际模块的内部连通图做全局遍历，再在最终几何上验证坡度、宽度与车辆净空。装饰失败可回退到合法简体模块；铁路/港口连通失败必须拒绝发布。

### 4.4 变形必须保住接缝与硬形

首个局部样区可采用四边形的双线性映射：`F(u,v)=(1-u)(1-v)P00+u(1-v)P10+uvP11+(1-u)vP01`，沿局部 up 加高度；需要弯曲体积时再用八角点映射。**这是项目拟用公式，不宣称 Oskar 用了这个公式。**

相邻模块必须引用同一边界曲线/采样顶点；不能各自随机扰动缝口。检查映射雅可比无翻转、退化面与过度拉伸，法线从变形后几何或导数重新生成。硬崖、台面边缘与城墙线保持约束；软坡内点可松弛。球面局部 chart 与可见海面共用曲率，不能仅将整根柱子转到某个 up 却留下浮空岩脚。

### 4.5 后台调度与事务发布

把纯数据求解放后台，几何/碰撞构建按实际渲染系统约束分段进行。一个作业带输入 revision；用户修改后旧结果即使完成也不得覆盖新场景。保持旧场景可用，候选经硬验证后整体交换；取消释放候选资源，不销毁正在使用的对象。限定单批构建预算并测量耗时，不能直接套用开发者旧硬件的毫秒数。

动作系统只消费通过验证的地面与路径。书店机器人可以使用邻近信息或局部避让来减少拥挤，但瞄准、脚部接触、运输承托、动画混合各自检验。若以后试验时间槽 WFC，必须展示候选域、邻接传播、矛盾处理以及超时合法回退，不能把状态机改名。

## 5. 实际仓库复用与最小验收

本轮阅读过入口，不等于完成链路审计或运行测试：

| 代码入口 | 已读内容 | 下一步应做 |
|---|---|---|
| `src/procgen/graph/irregularQuadGrid.js` | 三角格、配对、细分、松弛与锁点选项 | 不再新造同类网格；查边界锁定与跨块一致性 |
| `src/procgen/wfc/solver.js` | 确定性、传播、有限回溯、pins/bans、取消 | 接真实面状模块及整体约束 |
| `src/procgen/wfc/socketCompiler.js` | 旋转/镜像变体展开、接口签名去重 | 确认几何与语义均随变体正确转换；仅接口相同不必然表示美术变体相同 |
| `src/procgen/worker/jobProtocol.js` | 纯数据消息、schema、取消与结果协议 | 将几何发布与输入 revision 验证串起来 |

复现用例应包含：一个人工岩台样块；相同模块的确定性求解样块；被两端锁定的阶梯通道；一个故意不兼容接口；一个看似连通、内部被墙堵住的模块；一个用户快速改动导致旧任务迟到的案例。每种情况记录输入、预期与真实输出，失败案例必须正确拒绝。

视觉样区：三根蓝灰岩柱与一个低台，城堡只选港口上城口至翼楼。关闭雾后辨认宽台面和承托；中性日光与黄昏采用同一套本色检查；彩色及灰阶同机位对照。性能记录设备、画面规模、帧时和生成耗时。研究没有执行这些验收，不写“已通过”。

## 6. 尚不能宣布的结论

没有完整游戏源码、完整 shader 说明或已证实的 WFC 人物动作管线；没有证明 MFC/MCF 是作者统一引擎名称；没有把开源复刻当作作者实现。Imgur 本轮只读到索引正文片段，X 和大会覆盖由各自日志记录。当前可交付的是有边界的算法图谱与可复现实验规格，而不是宣布还原全部 Oskar 引擎。
