## 核心决策

按「玩家实际走过的场景」交付，不按模型文件逐个刷数量。72 项原作目录混合了单件、组合场景和生态子件，不能理解为 72 个等量任务，也不能把父场景与内部子件重复计算成果。

Web 保留可玩的原世界，作为场景关系、造型、动画与交互的对照；Blender 保存可编辑优化副本；Godot 逐区接回原作环境。现有紧凑 Godot 实验环境不是最终世界布局。每次明确改变的是哪个引擎，不暗示自动双端同步。

## 真实起点

- 72 项已有原作导出及 Godot 加载验证，但大部分仍缺运行时材质、动态行为和真实场景验收。
- 书店第三轮模型已接入 Web 与 Godot 主场景；入口/林带、碰撞、交信通过，Godot 原建筑墨线已接回。Godot 两阶明暗材质、完整书店镇仍未完成。
- 虎有参考与二维概念，当前三维仍是旧造型。既有拓扑整理不算虎的解剖重塑完成。
- 72 项不是全游戏清单：叹息之门、英雄与守军、八音盒等剧情对象，以及水面、云墙、粒子、程序动画与任务控制，须从实际场景调用补充登记，不能以导出目录冒充完整覆盖。

## 优先级与工作上限

1. 阻塞行走/交互、模型没进环境、接地/穿模、挡路和加载错误先修。
2. 玩家持续看到或主线依赖的角色与地标优先：书店、玩家、红狐、虎、叹息之门、苔庭、旧港和圣城。
3. 大面积地形和高重复植被优先统一风格及成本，再做次要小装饰。
4. 远景、纯装饰和非当前路线的变体最后细修，不无差别重做所有模型。

同时最多一个区域进入集成验收、一个独立角色或共用技术项制作；不要开启多片半成品区域。每个制作小批通常只取 3–5 个有明确依赖的资产。大场景拆成可测子批，不受这个数字机械约束。先交出一个完整可玩的区域，再扩大范围。

用户已明确要求利用并发。当前并行示范是 Web 书店石径回接与 Godot 书店两阶材质：分别指定文件所有者、输入源与验收输出，由主代理整合；共用源模型保持只读。同一前台 Blender 场景不得被多个执行者同时改写。后续角色/建筑/环境批也采用这种分工，而不是串行等待每个独立资产。

## 每项资产的账本与验收门槛

以现有 inventory/catalog/import-map 为身份来源，不再建立一份相互冲突的基础清单。续接记录须有：原来源、运行时调用及实际参数、所属场景/章节、父子依赖、优化副本、Web/Godot 各自状态、静态/动态节点、碰撞/交互、截图/动作证据、成本前后值、下一步和阻塞。

状态分开记录：已索引、已阅读、已归档、已导入、已优化、已回接、已验收。Web 与 Godot 独立列状态；未知写「未核查」，不从文件存在推导完成度。

每个资产或紧密组合必须完成：来源/引用核查 → 必要的参考与副本制作 → 材质/轮廓/尺度检查 → 接回实际环境 → 行走/动画/交互检查 → 相同镜头与灯光对照 → 性能与接手记录。未通过就留在当前批，不以批量导出替代。

性能以用户当前设备和固定视口测量，记录基线、绘制次数、图元、帧耗及内存，先定位瓶颈再定整场预算。软件渲染截图不当作硬件性能基准。重复实例导出展开的场景先恢复复用，保留动态节点，禁止盲目把全部网格合成一块。
