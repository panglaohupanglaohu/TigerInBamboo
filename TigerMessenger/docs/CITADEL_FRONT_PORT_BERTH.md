## 接入步骤（按顺序执行）

1. 用实际 boardingContract 与 Blender 动画展开跳板，校准候选俯仰；测真实端点、两边净空和连续脚面，不能仅凭求解器公式算通行。
2. 让原船员从船内中央通道依次取武器、走跳板到前港台面，再接现有城门→转折台→广场路径；保留同一角色身份。
3. 接入一艘现有巡航船的进港、停泊、离港状态，其他两艘和旧港剧情船保留。驾驶接管时让自动控制释放；离船之后明确返回巡航或泊位，防止瞬移。
4. 校验全海路线到此次局部进港入口，补全海床/动态船桨及转弯检查；局部成功不等于全海航行成功。
5. 接到默认 8931；把同一原资产、泊位、跳板与卸载路径同步到同一 Godot 工程，逐个启动/退出验证，避免多个 Godot 占内存。
6. 双端实际截图、玩家上下船、士兵卸载与重置均通过后，才将此项标为已接入。蓝帆是目标差距，后续作为阵营材质变体处理，保留原船材质版本。

## 实际跳板校准（最新）

旧求解器硬编码铰点 z=.48，但当前 Blender 帧210和资产合同为 z=.84。已改为读取 boardingContract，旧一轮坐标废止，以最新 berth-candidate.json 为准。

Web 新增 setBoardingPitch，保留原收回/外摆动画，仅最后20%过渡到岸面所需角度；不传角度时原行为不变。真实 hinge 端点与求解值误差 2.81e-7 米，三条接岸采样支持对象均为 front-harbor-walkable，两侧径向差约 -2.86/+2.97 厘米；尚不能称为完整脚面连续性验证。

Godot 原 warship-battle-v11 适配器增加显式 pose_boarding 接口，默认战斗仍收板。31个展开采样及恢复收板通过；误差1.19e-7米。测试 test_front_port_boarding_pose.gd 与证据 godot-boarding-pose.json。现有普通 tick 不自动驻留展开状态，后续码头控制器必须明确持有更新权。

下一步：船内通道、展开沿途的杆索/船员净空与真实士兵上下跳板。当前仅解决姿态和接岸点；不能以此宣称已完成卸载或完整战斗。

## 前港驻泊船实际合入

原 ocean-warship-0 由原数组同一对象改为前港驻泊，三艘总数不变，另外两艘仍巡航；旧港原船身份不变。F交互按岸端锚点可选船，原地上下船返回岸台，驾驶后在下船位置驻泊，不再被旧航线吸回。正式船保持收板，未启用已知存在穿插的旧展开序列。

Web 验证：web-resident-test.json，真实键盘 F 上下船及 WASD 短航程，前后 UUID 一致，旧船 UUID 一致，巡航数组3艘，停泊后位置漂移0，无页面错误。不是完整航道安全验证。

Godot front_harbor_berth_adapter 在原全局场景替换1个原快照 ocean-warship-0，使用同一v11资产/1.84比例/同一前港局部姿态，截图 godot-resident.png。仅原船装配与位置，Godot驾驶未迁移。

实际甲板检查使用原三兵种公开工厂+认可装备+携行姿态，在收帆展开人员姿态下每兵种两侧66点：短剑0交叉，弓箭0交叉，长矛1交叉（x=1.7,z=-.29 船头索具附近）。排除腿部以区分甲板接触，因此不能称全身行走通过。旧航行姿态下索具占道，必须先停船收帆再卸载。
