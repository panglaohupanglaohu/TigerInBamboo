## Blender 怎么做

1. 按资产清单读原工厂、调用参数、材质和动画引用，记录该模型不可改动的设计特征。批量候选不冒充已经通读和验收。
2. 原始快照保持不变，在有版本的工作副本中处理。保留节点名、关节、实例、UV、贴图、顶点色及原作单位关系。
3. 先处理能说明具体效果的问题：建筑接地、窗户被主体遮住、饰件穿插、台阶尺寸、破面和错误法线。仅根据已核实的实现缺陷修复，不把设计特点当错误。
4. 静态网格按材质和用途整理；动态角色与载具保持可动部件独立。碰撞代理单独建，不强迫渲染网格承担全部碰撞。
5. 批处理负责检查、导出和报告；具体造型修改逐项保留同机位前后图。数值整理要求外观一致；修复可见缺陷则要求差异准确对应修复目标。
6. Blender 预览材质与原 Web 着色器不能等同。墨线、透明、光源、粒子、程序动画分别记录适配状态。对于可复用原始法线的数据整理，继续沿用已经验证的无损回接方式。

现有脚本可以批量运行 Blender；前台交互已有 MCP 连接。根据任务选择批处理或前台操作，不把安装连接工具作为停止所有工作的理由。

## Godot 怎么做：先把原作真正放进工程

### 交付 A：原作资产检视场景（下一项优先交付）

- 建立 `godot/assets/originals/` 与逐项导入清单，原作名字与旧实验模型隔离，避免同名 bookshop、tiger 被误认。
- 从原作 Blender 档案/经过验证的工作副本导出 GLB，保留本地坐标、层级和材质槽。导出源和状态写入清单；未通过候选验证的部分采用原网格。
- 先用书店、虎狐、船、苔庭和圣城部件检验导出通路，再批量处理 72 项。测试必须涵盖贴图、实例、动态节点和组合场景，不能只用一个立方体代表全部成功。
- GLB 不足以表达的线条、粒子、着色器和程序逻辑，建立 Godot 专用场景/脚本适配任务。不得静默丢弃后标记完整导入。
- 制作 `godot/scenes/asset_review.tscn`：按名称/类别切换原作资产，自动取景，显示来源及缺失项；提供静止、动画和碰撞查看方式。大型整区按需加载，不同时塞进全部场景。
- 运行 Godot 导入检查并实际打开检视场景。用户应能在文件系统面板看到原作资源，在视口看到自己的书店、虎狐、湖沼和苔庭。

验收：72 项都有明确的“导入成功 / 部分适配 / 失败原因”记录，成功项能实例化；不得将失败项算完成。资产检视只是迁移入口，不等于世界和玩法已经完成。

### 交付 B：可见改善的出生点与书店镇

- 原 Web 先保存基准画面及可复现的缺陷位置，避免迁移和造型修复混在一起无法比较。
- 修复书店窗户遮挡、建筑与球面接地、台阶与角色通行、碰撞及明显阴影问题。
- 在 Godot 用原资产搭起对应的最小可玩区域，按原坐标、尺度和规则接入；旧紧凑关卡保留为历史实验，不继续作为成品入口。
- 提供同机位前后图和实际步行检查。原作画风一致，但修复的遮挡、悬空和通行问题应有可见变化。

验收：进入区域即可辨认原作；玩家能走完整条验收路线；建筑、台阶、门口无已知阻断；每项视觉改动能对应问题清单。

### 交付 C：球面世界、各区域与原作规则

- 球面移动、重力、相机朝向、地形高度与碰撞必须统一，不能靠摆一个球体代替球面玩法。
- 按书店镇 → 湖沼与虎狐 → 圣城 → 苔庭 → 科幻城市及载具扩展。每个区域完成模型、材质、碰撞、动画、交互与游戏回接后再标记可玩。
- WFC 与 Townscaper 风格拼装保留原模块、邻接规则、种子、接口与布局数据。先读取既有规则，再决定导入生成结果还是迁移生成器；不以随机堆房替代原规则。
- 按独立部件适配角色步态、八节尾巴、饮水、飞行和载具运动。静态导出不是动画迁移完成。
- 音效与光照围绕地点及行为设置：脚步、交互、机械、风水和救援反馈；先检验清晰度与整体风格，再调整数量和强度。

### 交付 D：完整救援体验与性能

把家书背景落实成可玩的过程：送信与获得能力、利用两个文明之间的战争牵制 aircraft、阻止吸食、救出湖沼之虎与红狐、撤离。现有六章状态框架不足以代替场景演出和互动。

完成后检查整条路线的引导、能力效果、跟随、失败/重试和存档。性能记录使用相同设备、相同路线和画质：帧时间、绘制调用、加载时间和内存。Blender 编辑顶点减少不作为帧率提升证据。
